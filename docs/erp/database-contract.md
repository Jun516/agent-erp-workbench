# ERP 业务账本与事务契约

本分支按用户要求把 ERP 作为核心业务。0409 是这个 ERP fork 的核心迁移；它没有把新表接入旧 CRM 的销售金额/库存字段，避免两个系统同时作为库存真相。原 CRM 的客户和沟通模块仍可独立使用。

## 接口与数据

- `lib/erp/contracts.ts`：命令输入的 Zod schema 与完整快照类型，页面、API、Agent 共用。
- `fn_erp_snapshot(p_org uuid,p_actor uuid) -> jsonb`：返回公司、仓库、供应商、SKU、余额、单据、明细、预占、流水、应收应付、审计和仓库授权。单据及数量只返回当前可见仓库；普通账号仅能看到自己的审计，管理员看到组织全部审计。
- `fn_erp_command(p_org uuid,p_actor uuid,p_command jsonb) -> jsonb`：每次命令必须带 UUID `idempotency_key`，成功返回 `{id,version?,status?,replayed}`。
- 仓库和产品通过同一公司复合外键约束；所有业务行带 `organization_id`。组织当前会员关系和状态在数据库再次验证，不能由请求正文决定租户。

所有 ERP 表开启 RLS，并撤销 `PUBLIC`、`anon`、`authenticated` 的表读写。业务 RPC 只授权给 `service_role`；内部库存 primitive 连 service role 都不可直接调用。服务端必须从已经验证的登录态取 actor/org。平台支持身份不自动扩大 ERP 会员权限。

## 可以执行的业务流程

1. 管理员建立公司、仓库、供应商和 SKU；建立一次期初库存，之后更正要用带原因的盘点调整，不能覆盖余额。
2. 销售单 `open` → 预占 → 分批出库 `partial` → `completed`。预占只减少可用库存；实际出库同时减少实物和预占，生成应收。没有预占不能直接出库。
3. 采购单 `draft` → `pending` → `approved` → `open` → 分批收货 `partial` → `completed`。采购下单只记录订单；验收时才增加实物库存，并按已收货净金额生成应付。
4. 未过账单据可取消并释放预占；已经收/发货的单据要使用逐行退货，不能抹掉流水。退货不能超过已处理减已退数量。
5. 同公司跨仓调拨在一个事务中一出一入；已预占的库存不可被调拨、退给供应商或负向盘点占用。
6. 应收应付允许手工分次登记银行/人工付款参考号，登记有版本和幂等保护。此动作不会调用支付接口。已核销金额高于退货后的新净金额时，整次退货拒绝并提示财务对账；本期未实现退款单、信用凭证或自动冲销。

所有成功命令在同一事务写入 `erp_audit` 和 `erp_command_receipts`。库存变化同事务写入 `erp_ledger`。失败时余额、明细、流水、应收应付一起回滚。没有外部采购或支付网络副作用。

## 权限、版本和幂等

- `viewer` 不能执行命令；`agent` 必须获得指定仓库的采购/收货/发货授权；`manager/admin` 拥有组织内仓库权限。基础资料、盘点、公司策略、授权、核销和审批需要管理员级业务角色（`manager/admin`）。
- 默认申请人与审批人分离；公司设置 `allow_self_approval` 可明确允许个人开发演示。`approval_limit_cents` 是公司采购审批硬上限，默认 10000000 分（100000 元），并非模型置信阈值。页面可调整。
- 采购草稿记录当时库存版本；提交、审批和下单都复验库存及关联销售单版本。期间变化会要求重建草稿，不能沿用旧审批。下单还复验审批人当前角色、公司当前额度和职责分离策略。
- 由销售单分析生成的采购必须提交 `source_order_version` 和完整 `source_stock_versions:[{product_id,version}]`；没有余额行时版本是 0。创建草稿时即比较模型原先看到的证据，防止刷新后把过期建议悄悄绑定到新库存。
- 关联采购的SKU必须属于源销售单，数量不得超过“该单未发未预占需求 − 当前可用库存 − 已关联且尚未收货的采购余量”，草稿也计入已承诺采购，防止连续点击创建两份补货。创建、提交、审批、下单都在锁内检查。额外安全库存应通过人工不关联采购表达，不能伪装为该销售单的缺口。
- 单据操作必须带 `expected_version`。前端刷新后应让用户重新核对；不要自动覆盖这个版本。
- 相同组织/幂等键/actor/正文重复请求返回原结果且 `replayed:true`。同键不同正文或不同 actor 拒绝。幂等记录不设置自动过期；它们是长期业务操作收据。
- 每个组织一个事务 advisory lock 串行化库存与调拨命令，因此不会出现两个仓库反向调拨死锁、重复收货或并发超卖。适合本地/小规模 self-host；高吞吐生产需要按公司/库存键细化锁及压测。

## 本期边界

基础版按整件数量和单据币种工作；不支持批次/序列号/保质期、BOM/MRP生产、在途运输跟踪、税务发票、汇率折算、总账分录、复杂成本核算。应收应付是业务净额台账，不能宣称完整财务软件或正式ERP上线业绩。

## 可复现验证

在项目根目录设置只指向临时数据库的 `ERP_TEST_DB_URL`，运行 `node scripts/erp-db-regression.mjs`。脚本不读取 `.env`，应用0409和0410两项ERP迁移，创建独立随机租户和账号，验证真实 PostgreSQL 事务、权限、幂等和并发，最后删除自己的测试数据。先按原仓库 canonical prelude 安装 baseline；`scripts/test-db.sh` 提供该前置环境。

结果写入 `docs/erp/qa/database-results.json`，包括真实数据库版本和逐条通过项目。不要把该结果理解为模型或 Jev 的准确率。
